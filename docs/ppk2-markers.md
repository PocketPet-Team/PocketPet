# PPK2 logic markers

> **Status:** Provisional. The Zephyr application drives these lines and builds for the nRF52840 DK, but it has not run on hardware and no capture has been taken with them. The layout and the DK pins can still change.

The firmware labels a power capture by driving GPIO lines into the PPK2's logic port. The analysis in [`experiments/`](../experiments/README.md) reads those lines to assign every current sample to one operating state and to charge each event only for what it draws above that state's background.

## Layout

The layout is defined once, in [`firmware/core/marker.h`](../firmware/core/marker.h). Line n is meant for PPK2 logic channel Dn.

| Line | Carries | High while |
| --- | --- | --- |
| 0 | State code, bit 0 | See the state table |
| 1 | State code, bit 1 | See the state table |
| 2 | `button` event | A button press is being handled |
| 3 | `haptic` event | The Find indication is on |
| 4 | `transfer` event | A state update is waiting to be transmitted |

Lines 0 and 1 form a binary code, line 0 least significant.

| Code | State | Meaning |
| --- | --- | --- |
| 0 | `idle` | No link and not advertising. This covers boot and the gap between a disconnection and the restart of advertising. |
| 1 | `adv_fast` | No link, advertising at the fast interval |
| 2 | `adv_slow` | No link, advertising at the slow interval |
| 3 | `connected` | A link is up |

All lines are low before the firmware configures them, so the time before that reads as `idle` with no event.

PPK2 channels D5 to D7 are unused. Motion wakes (RQ1) and a display refresh that is separate from a button press (RQ4) have no line yet.

## When the lines change

- **State.** The firmware updates the state lines after it has applied each queued event. On link loss the code changes to `adv_fast` once the call that restarts advertising has returned. On connection it changes straight from an advertising state to `connected`.
- **`button`.** Raised in the button interrupt when a press passes the 50 ms lockout, lowered after the display refresh for that press has been applied. The pulse therefore includes the wait for the work item. A press that arrives while the line is still high joins the open pulse.
- **`haptic`.** Raised when the Find indication starts and lowered when it ends. A Find request that arrives during an indication extends the same pulse.
- **`transfer`.** Raised when a state notification is handed to the Bluetooth stack and lowered when the stack reports it transmitted. The line is also lowered on disconnection, because the stack drops an unsent notification without reporting it.

## Manifest fragment

[`firmware/app/ppk2-markers.json`](../firmware/app/ppk2-markers.json) holds the layout as the `markers` object of a run manifest. Copy it into the manifest of every capture taken with this firmware. It assumes line n is wired to channel Dn, so edit the channel numbers if a rig is wired differently.

The file is generated by the host tool `marker_map` from the same header the firmware compiles, and a host test fails when the two disagree:

```sh
cmake -S firmware/host -B build/pet-host
cmake --build build/pet-host
./build/pet-host/marker_map > firmware/app/ppk2-markers.json
ctest --test-dir build/pet-host -R marker --output-on-failure
```

The layout is part of the capture format. A capture is only readable with the fragment that matches the firmware commit recorded in its manifest.

## Wiring on the nRF52840 DK

These pins are a provisional bench assignment from [`firmware/app/boards/nrf52840dk_nrf52840.overlay`](../firmware/app/boards/nrf52840dk_nrf52840.overlay). The DK's devicetree in NCS v3.4.2 assigns none of them to a peripheral. The compact board will choose its own pins.

| Line | DK pin | Arduino header label | PPK2 channel |
| --- | --- | --- | --- |
| 0 | P1.03 | D2 | D0 |
| 1 | P1.04 | D3 | D1 |
| 2 | P1.05 | D4 | D2 |
| 3 | P1.06 | D5 | D3 |
| 4 | P1.07 | D6 | D4 |

The logic port also needs a reference voltage and ground. Follow Nordic's [Logic port](https://docs.nordicsemi.com/bundle/ug_ppk2/page/UG/ppk/logic_port.html) guide for those connections and for the supported voltage range.

Another board supplies its own lines with a devicetree node:

```dts
/ {
	ppk2-markers {
		compatible = "pocketpet,ppk2-markers";
		gpios = <&gpio1 3 GPIO_ACTIVE_HIGH>, /* one entry per line, line 0 first */
			...;
	};
};
```

The lines must be SoC GPIOs because the firmware drives them from interrupt context. Without such a node, or with `CONFIG_POCKETPET_PPK2_MARKERS=n`, the firmware drives no markers.

## Not verified yet

- **Nothing here has run on a board.** Pulse widths, edge timing against the current trace, and the delay between a radio event and its state change are unmeasured.
- **The `button` pulse may be very short.** With an LED standing in for the display, the pulse lasts only as long as the work item takes to run. If that is shorter than the PPK2's sample period, a capture can miss it. Check this on the DK before counting button events from a capture.
- **A state change that flips both lines is written one line at a time.** Interrupts are masked during the write, so the gap should be far below one sample, but a capture can still show the code in between for a single sample. `adv_fast` to `adv_slow` passes through `idle`, and `connected` to `idle` passes through `adv_slow`.
- **The state lines follow the firmware's decisions.** If the stack refuses to start advertising, the log reports the error and the lines still read `adv_fast` or `adv_slow`.
- **The marker lines are a load on the measured supply.** How much current the logic port draws from a high line has not been measured. Compare a capture with `CONFIG_POCKETPET_PPK2_MARKERS=n` before treating marked captures as representative.
